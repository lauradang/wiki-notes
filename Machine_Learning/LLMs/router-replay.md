# Router Replay (R3)

**Router replay** makes the trainer send each token through the same experts the inference engine used when it generated that token. It does this by recording the expert choices during generation and replaying them during training.

## Background: MoE, routers, routes

- **MoE (Mixture of Experts):** the usual feed-forward block in each transformer layer is replaced by many smaller feed-forward networks called **experts**. For example, a layer might have 64 experts.
- **Router:** a small linear layer that gives every expert a score for each token.
- **Top-k:** the token goes only to the `k` experts with the highest scores (often `k` = 2 to 8). Their outputs are blended using weights derived from the scores.
- **Route:** the set of experts a token used in one MoE layer. A token gets one route per MoE layer, for example `{2, 5}` in layer 0 and `{11, 40}` in layer 1.
- **Prefill:** the step where the engine reads a whole known prompt in one forward pass, before it starts generating new tokens.
- **Logprobs:** the log-probability the model gave to each token it produced. RL compares these numbers between the model that sampled the text and the model being trained.

## How inference and training can disagree

The text is generated by an **inference engine** (in NeMo-RL that's vLLM or Megatron Inference). The model is trained by a different **training engine** (Megatron, or FSDP). Same weights, but different code paths:

- different kernels (the low-level GPU functions that do the math)
- different precision and accumulation order (floating-point addition isn't associative)
- different batching and padding
- different parallel layouts (TP/EP — how the model is split across GPUs)

Each of these shifts the router scores a little, say in the fourth decimal place. Picking the top-k is a **discrete** choice, though. If two experts are almost tied, a tiny score change swaps which one wins. **A small numeric difference turns into a different path through the network.**

```
                 INFERENCE ENGINE (vLLM / Megatron Inference)
  ┌────────┐     ┌──────────────────────────┐     ┌────────────────────┐
  │ "cat"  │ ──▶ │ router scores            │ ──▶ │ experts {2, 5}     │ ──▶ sampled text
  └────────┘     │ e2=0.41 e5=0.300 e7=0.299│     │ ┌──┐ ┌──┐          │     + logprob  -1.20
                 └──────────────────────────┘     │ │E2│ │E5│          │
                          top-2 → {2, 5}          │ └──┘ └──┘          │
                                                  └────────────────────┘

                 TRAINING ENGINE (Megatron / FSDP) — same weights, same tokens
  ┌────────┐     ┌──────────────────────────┐     ┌────────────────────┐
  │ "cat"  │ ──▶ │ router scores            │ ──▶ │ experts {2, 7}  ✗  │ ──▶ recomputed
  └────────┘     │ e2=0.41 e5=0.299 e7=0.300│     │ ┌──┐ ┌──┐          │     logprob  -1.35
                 └──────────────────────────┘     │ │E2│ │E7│          │
                    tiny diff flips the tie       │ └──┘ └──┘          │
                          top-2 → {2, 7}          └────────────────────┘

  Result: the trainer computes logprobs and gradients through a DIFFERENT
  sub-network than the one that actually wrote the text
     → off-policy mismatch → train/inference logprob error grows → RL instability
```

The numbers in the diagram are made up to show the effect. They aren't measurements.

## Why it matters for RL

- GRPO and PPO compare "how likely was this token under the policy that sampled it" with "how likely is it under the policy I'm updating" (the importance ratio, built from logprobs).
- That comparison only makes sense if the trainer is evaluating the **same policy** that did the sampling.
- With MoE, the expert path is part of the policy. Re-routing a token through different experts means the trainer is scoring a slightly different model. That shows up as noisy ratios, a growing train/inference logprob gap, and unstable training.

## With router replay

```
  INFERENCE ENGINE                                   TRAINING ENGINE
  ┌──────────────────────────────┐                   ┌──────────────────────────────────┐
  │ "cat" → router → {2, 5}      │                   │ "cat" → router ─╳─ own top-k     │
  │                    │         │                   │           ▲      ignored         │
  │                    ▼         │                   │           │ forced: {2, 5}       │
  │   record route per token,    │                   │           │                      │
  │   per MoE layer              │                   │      ┌──┐ ┌──┐                    │
  └────────────┬─────────────────┘                   │      │E2│ │E5│  same path         │
               │                                     │      └──┘ └──┘                    │
               ▼                                     │           │                      │
  ┌─────────────────────────────────┐   travels      │           ▼                      │
  │ routes tensor                   │   with the     │   logprob -1.20  ✓ matches       │
  │ [tokens, MoE layers, top_k]     │ ─────────────▶ └──────────────────────────────────┘
  │ int expert ids, e.g.            │   rollout
  │ routes["cat"][layer 0] = [2, 5] │
  └─────────────────────────────────┘
```

- During generation, the inference engine saves the chosen expert ids for every token in every MoE layer.
- That tensor is sent to the trainer as part of the rollout, next to the tokens, logprobs and rewards.
- The trainer's router is overridden to use the recorded expert ids, so each token goes to the same experts as during generation. The trainer still does its own math inside those experts, including how much weight each chosen expert gets. Only the *choice* of experts is fixed.
- Same path means matching logprobs, so the importance ratio measures what it's meant to measure.

## Route values the trainer can see

| Route value | Meaning | Trainer behavior |
|---|---|---|
| Real expert ids, e.g. `[2, 5]` | The engine recorded this token's route | Replay it: use exactly these experts |
| `-1` in every entry | No route was recorded for this token | Ignore replay here and let the trainer's own router decide |
| Fake `0, 1, …, k−1` (old bug) | A gap filled with placeholder ids | **Looked real**, so it was replayed and the token was sent to the wrong experts with no error |

## Multi-turn stitching and the turn-boundary token

A multi-turn rollout (assistant → tool → assistant) is made of several inference calls. Each call saves routes only for its **new** tokens, and the pieces are joined into one row afterwards.

The key rule: **an engine records a token's route only when that token is fed *into* the model.** A token that was just sampled hasn't gone through the model yet.

```
  positions:   p0  p1  p2 │ p3  p4 │ p5      │ p6  p7  p8  p9
               └ prompt ──┘ └gen 1─┘  tool     └──── gen 2 ───┘

  CALL 1  prefill p0–p2, generate p3, p4
          fed in:  p0 p1 p2 p3            ← p4 was sampled but never fed in
          routes:  ✓  ✓  ✓  ✓  —          → call 1 has NO route for p4

  CALL 2  prefill p0–p5 (re-reads p0–p4 + tool token p5), generate p6–p9
          fed in:  p0 p1 p2 p3 p4 p5 p6 p7 p8   ← p4 IS fed in during this prefill
          routes:  ✓  ✓  ✓  ✓  ✓  ✓  ✓  ✓  ✓  —   → call 2 HAS p4's real route
                                                     (p9 never fed in)

  prev_len = 5 (tokens already in the row before call 2: p0–p4)

  OLD (bug):  call 2 keeps experts[prev_len:]   = p5..p8
              p4's slot stays empty → vLLM filled it with fake 0,1,…,k−1
              → trainer replays fake experts for p4

  FIX:        call 2 keeps experts[prev_len-1:] = p4..p8   (one extra "boundary" row)
              and writes that row into p4's slot → p4 gets its REAL route

  final row:   p0 p1 p2 p3 p4 p5 p6 p7 p8 p9
               ✓  ✓  ✓  ✓  ✓  ✓  ✓  ✓  ✓  -1
```

- The old bug hit **the last token of every non-final assistant turn**, without any error. That token is exactly where the model hands off to the tool.
- The very last token of the whole row (`p9`) never gets a route, because nothing is generated after it. That's harmless: the model doesn't predict anything *from* `p9`, so its route never affects a logprob. It's marked `-1`.
- In general, `-1` means "no recorded route, trainer, use your own router." It is never confused with a real expert id.

## Cost and gotchas

- **Size:** routes form a large integer tensor, `[tokens × MoE layers × top_k]`, that has to travel with every rollout.
- **Exact length bookkeeping:** on every call after the first, each backend must stage `delta_len + 1` rows: the new tokens plus the boundary row. `delta_len` is the number of new tokens in that call.
- **Off-by-one shows up only on multi-turn:** a backend that stages one row too few gets every multi-turn rollout rejected, while single-turn still works. A short single-turn smoke test can pass and hide the bug.
- **Every backend must agree:** in NeMo-RL, vLLM and Megatron Inference both feed the Megatron trainer, so they have to follow the same row conventions: boundary row, `-1` for "no route", no placeholder ids.

## TL;DR

- MoE routers make discrete top-k choices, so tiny numeric differences between inference and training can flip which experts a token uses.
- That puts the trainer on a different sub-network than the one that sampled the text: an off-policy mismatch and unstable RL.
- Router replay records `[tokens, layers, top_k]` expert ids during inference and forces the trainer to use them.
- In multi-turn rollouts, a turn's last token only gets its route in the *next* call's prefill. Keep one boundary row (`experts[prev_len-1:]`), and use `-1`, never fake ids, for "no route".
